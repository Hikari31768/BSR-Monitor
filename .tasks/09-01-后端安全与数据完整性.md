# 09-01 - 后端安全与数据完整性修复

## 优先级：P0（阻断后续工作）

## 背景

08-01（API 模块）和 08-02（数据库层）Review 中发现的 CRITICAL 问题，涉及数据不一致、崩溃风险、序列化安全。

## Review 问题来源

- [08-01-API模块Review.md](08-01-API模块Review.md) 第 64-104 行
- [08-02-数据库层Review.md](08-02-数据库层Review.md) 第 68-92 行

## 具体任务

### 1. 数据库事务保护

**1.1 删除操作事务化**

- [ ] `delete_player`（`database/operations.rs`）：包裹在显式事务中，确保 PlayerScore 和 PlayerInfo 的删除原子性
- [ ] `delete_playlist`（`database/operations.rs`）：包裹在显式事务中，确保 PlaylistMap 和 Playlist 的删除原子性

**1.2 插入操作事务化**

- [ ] `add_player` 命令中 `insert_map` + `insert_map_diffs_batch` + `insert_playlist_map` 组合操作应包裹在统一事务中
- [ ] `add_playlist` 命令中同样问题
- [ ] `save_playlist_maps_with_progress` 中每个谱面的 Map/MapDiff/PlaylistMap 三次独立锁获取应合并为一次事务

**1.3 多步原子性操作规范**

- [ ] 定义辅助函数 `fn with_transaction<F>(conn: &Mutex<Connection>, f: F) -> Result<(), String>` 简化事务管理
- [ ] 文档注释说明哪些操作必须在事务中执行

### 2. 外键约束启用

- [ ] `init_database`（`database/mod.rs`）中创建连接后执行 `conn.execute_batch("PRAGMA foreign_keys = ON;")`
- [ ] 确认 schema.rs 中定义的 FOREIGN KEY 约束在外键启用后不会导致现有数据冲突
- [ ] 手动级联删除逻辑（`delete_player` 先删 PlayerScore）在外键启用 + `ON DELETE CASCADE` 后可简化，但当前 schema 未定义 CASCADE，需先迁移

### 3. 序列化安全（serde default）

**3.1 BeatLeader 响应结构体**

- [ ] `PlayerResponse`（`api/types.rs`）：对可能缺失的字段添加 `#[serde(default)]` 或改为 `Option<T>`
  - `country`: 改为 `Option<String>` 并添加 `#[serde(default)]`
  - `avatar`: 添加 `#[serde(default)]`
- [ ] `CompactScore`：确认 `base_score` 和 `modified_score` 是否仍被业务层使用，若不使用则移除
- [ ] `Metadata` 分页结构体：对 `itemsPerPage`、`page`、`total` 添加 `#[serde(default)]`
- [ ] `CompactLeaderboard`：对所有非主键字段添加 `#[serde(default)]`
- [ ] `SongResponse`、`DifficultyResponse`：同样处理

**3.2 难度类型安全**

- [ ] `CompactLeaderboard.difficulty` 从 `i32` 改为类型安全的枚举或添加范围校验
- [ ] `PlaylistType` 的 `#[serde(rename_all = "PascalCase")]` 改为 `lowercase` 或通过实际 API 验证

### 4. API 客户端 panic 修复

- [ ] `ApiClient::new()`（`api/client.rs`）：将 `.expect("Failed to create HTTP client")` 改为 `Result` 返回
- [ ] 或提供降级方案：`unwrap_or_else(|_| Client::new())` 回退到默认 Client
- [ ] 更新所有调用 `ApiClient::new()` 的命令层代码以处理 Result

### 5. 重试机制改进

- [ ] `request_with_retry`（`api/client.rs`）：超时和 429 限流应分别计数，或改为独立的计数器
- [ ] 429 重试时读取 HTTP `Retry-After` 响应头，而非硬编码 60 秒
- [ ] 重试循环改为 `for attempt in 0..=max_retries` 模式提高可读性

### 6. 数据库索引优化

- [ ] 创建复合索引 `(playerId, hash)` 替代单独的 `idx_playerscore_hash` + `idx_playerscore_player`
- [ ] 评估 `idx_playerscore_player` 在新增复合索引后的价值，考虑移除冗余索引

### 7. 边界情况修复

- [ ] `parse_leaderboard_id`（`database/operations.rs`）：使用 `rsplit_once('x')` 替代 `split('x')` 处理多个 'x' 的情况
- [ ] `parse_leaderboard_id`：对空字符串、单字符输入增加显式错误返回
- [ ] `insert_score` 的 SELECT-then-UPDATE/INSERT 模式：在事务中执行或使用 `INSERT ... WHERE NOT EXISTS` 避免并发竞争
- [ ] URL 路径参数（`player_id`、`hash` 等）添加 URL 编码处理
